天池 Research Agent 开放域问答

单题 55 秒的开放域事实问答 Agent：先直答再按需检索，多源并发搜索、二跳补证据、答案归一化，用 SSE 流式返回。

面试开场可以这样讲

这是阿里云 Data+AI 大赛 Agent 赛道的开放域事实问答，评测按答案精确匹配，单题限时 55 秒。我独立完成了整个服务：外层用 AgentScope Runtime 部署成接口，主流程是我手写的有限级联——先让模型直答并校验，不通过才改写查询、多源并发搜索、二跳补证据、基于证据作答，最后按题型归一化答案；所有步骤共享一个截止时间。迭代过程中我按题回放错误、区分检索遗漏、推理和格式问题，本地评测准确率从 13% 提升到 52%，最终复赛第 44 名。

背景与问题

开放域事实问答的难点不在“能不能调用搜索”，而在三个取舍：什么时候该搜（简单题直答更快更稳，每题都搜会引入噪声和延迟）；搜到什么程度（多跳题第一轮往往只命中中间实体）；时间不够时怎么退出（55 秒里要给模型、搜索、校验和回包分配时间）。另外评测是精确匹配，事实对了但格式不对（年份带“年”、中英文名不一致）同样不得分。

团队

以团队名义报名参赛，系统设计与代码由我一人完成。

整体流程

  1. 接收问题记录截止时间，后续每步按剩余时间算时限
  2. 直答 + 校验格式、长度、不确定表达、题型匹配
  3. 查询改写关键词抽取、问题拆分为子查询
  4. 多源并发搜索IQS / Tavily / SerpAPI，单源超时进入冷却
  5. 排序与二跳可解释排序取 Top-N，缺证据时按实体补搜
  6. 证据作答 + 升级主模型不通过时升级 qwen-plus
  7. 归一化与退出按题型整理答案，或返回 unknown

核心技术点

每一点都按“怎么做 → 为什么 → 代价”整理

1. 有限级联，而不是开放式 ReAct

怎么做主流程是固定的几步：直答 → 校验 → 检索 → 证据作答 → 强模型兜底 → 归一化，由代码决定是否升级。LangChain create_agent（底层是 LangGraph 的 ReAct 图）挂载三个搜索工具，作为可选分支保留，默认关闭。

为什么55 秒内要精确控制每一步的耗时和调用次数。固定流程每步可预测、好调试；ReAct 的循环次数和延迟不可控。

代价与改进代价是失去根据工具反馈灵活改路线的能力。如果题目需要更多轮推理，可以给 ReAct 设最大步数和单步时限后再打开。

2. 时间预算：一个总截止时间，单步时限动态计算

怎么做进入时设 deadline = now + 55 秒，每一步的时限 = min(该步默认值, 剩余时间 − 安全余量)。剩余时间不够一次完整调用时就不再发起，留出校验和回包的时间。

为什么固定的单步超时加起来会超过总时限；按剩余时间分配，前面的步骤慢了，后面会自动收紧。

代价与改进代价是后面的步骤可能分不到时间，所以把最可能出答案的直答放在最前面。

3. 多源并发搜索与故障隔离

怎么做三个搜索源用 asyncio 并发调用，统一成同一种结果结构后去重；某个源超时或报错就进入 300 秒冷却，冷却期间不再调用，其余源照常工作。

为什么搜索主要是网络 I/O，并发能把串行耗时降到最慢的那一路；冷却避免一个坏掉的源每题都拖满超时。

代价与改进更多源意味着更多噪声和结果冲突，所以后面必须有排序和证据预算。

4. 查询改写与二跳检索

怎么做从问题里抽取关键实体和限定词改写查询，复杂问题拆成最多 2 个子查询；如果第一轮只命中了中间实体（比如“某基金会”），就从结果里抽出实体再补搜一次，最多 2 个实体。

为什么多跳问题直接搜原句，往往只能搜到第一跳；显式拆开再补搜，比让模型自己决定更可控。

代价与改进二跳会增加一轮延迟，所以只在证据不足且剩余时间足够时触发。

5. 可解释的证据排序

怎么做按标题覆盖、词项重叠、年份和实体一致性、来源等信号给结果打分，过滤掉与问题词项重叠不足 2 个的文档，取 Top-N 并限制字符数后注入提示词。

为什么排序依据可以逐条解释，出错时能看出是哪个信号失效；比赛环境下也不方便再部署一个重排模型。

代价与改进规则排序的上限有限；更好的做法是用标注好的查询集比较规则排序与交叉编码器，测 nDCG 和端到端正确率。

6. 答案校验与按题型归一化

怎么做先识别题型（年份、数字、页数、中文名、英文名），再清洗候选：去掉解释性前后缀、工具轨迹和“不确定”表述，数字统一格式，中英文名按题目要求取对应语言。

为什么精确匹配评测下，格式错误和事实错误一样扣分；回放发现有相当一部分失分来自格式。

代价与改进规则覆盖不到的格式会漏掉，所以每次回放都把新的格式错误补进规则。

7. SSE 流式接口与取消

怎么做/answer 同时支持 JSON 和 SSE。流式模式下先发 Ping 事件保持连接，答题任务在后台运行，等待期间每 15 秒一次心跳，完成后用 Message 事件返回答案；客户端断开时捕获取消，并取消后台答题任务。

为什么评测网关对长时间无数据的连接会断开；心跳和结果分成两种事件，前端能区分“还在等”和“已完成”。

代价与改进心跳只说明连接还活着，不代表模型在产出；排查卡住的请求要看任务状态，不能只看有没有心跳。

难点与排查

从“每题都搜”到“按需检索”：一次按题回放的错误归因

  1. 现象早期版本对所有题都先搜索再作答，评测准确率只有 13%，平均耗时也高，很多本来直答就能对的简单题反而答错了。
  2. 定位把错题逐题回放，按“检索没找到 / 找到了但推理错 / 答案对但格式不符”三类归因：简单题被搜索结果里的噪声带偏，多跳题第一轮只命中中间实体，还有不少是格式错误。
  3. 改动改成直答优先、校验不通过才检索；加入多源召回和重排；对多跳题做查询拆分和二跳补搜；最后补齐按题型的答案归一化。
  4. 结果每一步都在同一批题上回归，准确率从 13% 逐步提升到 52%，耗时也随直答比例上升而下降。

常见追问

这是 RAG 吗？和自建知识库的 RAG 有什么不同？

是检索增强生成，但检索来自运行时调用的外部搜索 API，不是自建向量库。我能控制的是查询构造、多源融合、排序和证据注入；搜索引擎内部的召回不在我的控制范围，所以重点放在“搜什么”和“用哪些结果”。

为什么不用 ReAct？

试过，也保留在代码里，但默认关闭。55 秒的硬时限下，ReAct 的步数和延迟不可控；固定级联每一步可预测，出错也能定位到具体环节。题目更开放、时限更宽松时，我会给 ReAct 加最大步数和单步时限再用。

13% 到 52% 的提升分别来自哪里？

按版本看：证据作答 +12 个点，多源召回与重排 +8，查询拆分和二跳 +8，提示词与格式 +7，错题归因与归一化 +4。这是逐版本叠加的结果；要严格证明单个模块的贡献，需要在固定题集上做消融，每次只去掉一个模块。

搜索源一直超时怎么办？

单源超时或报错就进入冷却期，冷却内不再调用，其余源照常；所有源都失败时，回到直答结果，校验不通过就返回 unknown，不强行猜。

页面一直有心跳但迟迟没有答案，怎么排查？

心跳只说明连接在。先看后台任务是否还在运行、卡在哪一步（通常是某个外部调用），再看是否已经发出终态事件而前端没解析到。

如果放到真实业务里，你会补什么？

三样：按题型拆分的线上指标（准确率、unknown 比例、p95 延迟、工具调用次数）；检索结果缓存（按标准化问题、带过期时间）；对有副作用的工具加幂等和人工确认。

复盘：如果重做

  • 用标注好的查询集做排序消融（规则排序 vs 交叉编码器），用 nDCG 和端到端正确率说话，而不是只看总准确率。
  • 把每题的运行轨迹（每步耗时、调用的源、候选、终止原因）结构化存下来，回放和归因可以自动化。
  • 评测报告按题型拆开：年份题、人名题、多跳题的瓶颈完全不同。
